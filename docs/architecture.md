# Архитектура dvarp-lab

Схема владения и связи полигона с СС для проверки гипотез исследования.
Прототип-референс: dvarp-prototype @ d5828df (защита переносится как есть).

## Компоненты

| Компонент | Роль | Эндпоинты |
| --- | --- | --- |
| `shop_svc` | БД магазина + процесс возврата с ИИ-агентом: гвардрейлы (пассивность),
  политика реакции, инструменты агента, права исполнителя, правила эскалации,
  внутренний журнал | `/reset`, `/snapshot`, `/snapshot/{id}`, `/turn`, `/configure` |
| `traffic_svc` | Симуляция безопасного трафика: реальные возвраты на основе БД магазина
  (читает её для правдивых запросов), стили общения (заморожены) | `/run-episode` |
| `attack_svc` | Симуляция атаки: корпус атак (заморожен), тактика назначается планом
  прогона, бюджет; ходит только текстом; сигналы начала/конца атаки | `/run-episode`, `/start`, `/stop` |
| `filter_svc` | Фильтрация: разделение ответа и сырых внутренних данных; наружу — только
  текст; сырьё + снимки состояния + кассеты пишет в свою БД (хеш-цепочка) | `/record`, `/text/{episode}` |
| `metrics_svc` | Расчёт метрик (L* и формулы канона) поверх сырой БД — запускается в любое
  время, результаты в своей БД, агрегация по config × model | `/compute`, `/metrics/{config}` |
| `launcher` | Скриптовый оркестратор: перебор сетки «модель × конфигурация × сценарии
  взаимодействия», выбор конфига + seed, сброс БД магазина, номинальные проверки,
  парные прогоны, триггер расчёта метрик | CLI |

## Потоки данных

1. `launcher`: выбирает конфиг + seed → номинальная проверка → сброс БД магазина
   → парные прогоны (легальный + атакующий трафик на одном конфиге) → при желании
   триггерит расчёт метрик (может быть запущен в любое время).
2. `traffic_svc` читает БД магазина для создания правдивых запросов на возврат;
   диалог идёт «только текст ответа» через `filter_svc`.
3. `attack_svc` получает размеченные стартовые промпты корпуса + тактику из плана
   прогона; без доступа к защите и БД магазина; наружу — только текст.
4. `shop_svc` пишет в БД магазина («запись о возврате», «чтение для проверки
   реальности возврата») и отдаёт `filter_svc` «текст + снимок состояния».
5. `filter_svc` сохраняет «данные для расчёта» и «снимок состояния» в свою БД,
   возвращает симуляциям только текст.
6. `metrics_svc` считает L* и сохраняет «L* для конфига» в свою БД.

## Замороженные характеристики (frozen/)

- `configs/*.json` — конфигурации защиты (из прототипа @ d5828df);
- `llm.json` — ростер моделей (имя, размер, версия весов); меняется редко и осознанно;
- `corpus/` — корпус атак;
- `styles.json` — стили общения легального трафика.

## Принципы

1. **Сбор ≠ расчёт.** В процессе прогона только сбор сырых данных. Метрики —
   отдельным сервисом, когда угодно, поверх сохранённого; правка формул не требует
   перезапуска прогонов.
2. **Пин модели.** Каждый прогон и каждое хранилище (журнал shop, запись attack,
   сырьё filter, агрегаты metrics, манифест launcher) фиксируют `model_spec`
   (агент поддержки и атакующий — раздельно).
3. **Seeds.** Детерминированные части (раскладка эпизодов, заглушки) — от seed;
   живая модель недетерминирована — реален трейс (сырые транскрипты).
4. **Журнал — хеш-цепочка** (JSONL, seq/prev/hash). **Кассеты** — по строке на пару
   запрос→ответ к модели.
5. **Сеть без охраны.** Вместо сетевой изоляции — номинальная проверка конфигурации
   перед каждым прогоном (см. `lab/nominal.py`).
6. **Сервисы для читаемости.** Код повторяет схему 1:1; обмен — HTTP на локальных
   портах; PostgreSQL (запуски) / SQLite (тесты) через SQLAlchemy.
