# Мануал агента dvarp-lab: структура, потоки, критичные инварианты

Актуально на срез: происхождение подсистем — [PROVENANCE.md](PROVENANCE.md) (карта вклада); схема v3 (фильтрация/расчёт L* разделены, UI-блок). Обновлять при изменении механики.
Схема полигона: [docs/scheme.svg](scheme.svg). Контракты эндпоинтов: [docs/api.md](api.md).
Общая архитектура: [docs/architecture.md](architecture.md).

## Зачем эта репа

Полигон проверки гипотез исследования (статья): защита СС «магазин возвратов»
измеряется под легальным и атакующим трафиком. Построен на принципах:
**сбор ≠ расчёт**, **барьер «только текст»**, **пин модели в каждой записи**,
**замороженные характеристики**. Всё в одном репо, сервисы — для читаемости кода.

## Структура каталогов

| Путь | Что это |
| --- | --- |
| `lab/` | Общая мини-либа: `chain.py` (хеш-цепочка журнала), `cassette.py` (кассеты), `seeds.py`, `modelspec.py` (ростер frozen/llm.json), `nominal.py` (номинальная проверка), `db.py` (SQLite dev / PostgreSQL prod), `svc_client.py` |
| `services/shop/` | СС: БД магазина (`db.py`), защита (`guards/` — перенесена из прототипа), агент (`agent/`, `agent/llm`), журнал (`journal/`), FastAPI-приложение (`app.py`) |
| `services/traffic/` | Симуляция безопасного трафика: стили (`style.py`), правдивые возвраты из БД (`case.py`), цикл эпизода (`episode.py`) |
| `services/attack/` | Симуляция атаки: методы давления (`tactics.py`), цели — замороженные претензии поверх данных мира (`frozen/corpus/goals.json` + `lab/world.py`), атакующий (`attacker.py`), цикл (`episode.py`); промпт собирается без обращений к shop | `/run-episode`, `/start`, `/stop` |
| `services/filter/` | Сырая БД + хеш-цепочка + кассеты; наружу — только текст |
| `services/metrics/` | Формулы канона (`formulas.py`: L*, break-even, detection) поверх сырой БД |
| `launcher/` | Скриптовый оркестратор: матрица, seeds, номинальные проверки, парные прогоны |
| `frozen/` | Замороженные характеристики: `configs/`, `llm.json`, `corpus/` (методы атаки + цели), `styles.json`, `seed_worlds/world_a/` (единственный мир БД) |
| `scripts/smoke.py` | Сквозной смок: поднимает 5 сервисов, гоняет launcher, считает метрики |
| `tests/` | pytest: перенесённые тесты защиты + новые сервисные/golden |

## Как запускается

```sh
uv sync                                        # зависимости (Python 3.13 через uv)
uv run pytest                                  # все тесты
uv run python scripts/smoke.py                 # сквозной смок (5 сервисов + прогон + метрики)
# сервисы по одному:
LAB_SHOP_DB_URL=sqlite:///shop.db uv run uvicorn services.shop.app:app --port 9411
# прогон кампании (сервисы должны быть подняты):
uv run python -m launcher run --config g0 --episodes 2 --compute
```

## Поток данных (по схеме)

1. `launcher/__main__.py:run()` — ячейка матрицы (config × goal × style × tactic):
   номинальная проверка → `POST shop /reset {seed}` (сброс к замороженному миру;
   пин `world`/`dataset_hash` в манифесте) → `POST shop /snapshot` →
   легальный эпизод (`traffic /run-episode`) → `restore` → атакующий эпизод
   (`attack /run-episode`, цель ячейки) → `restore`; манифест в
   `runs/<run_id>/manifest.json`.
2. Симуляции ходят только текстом: `traffic` и `attack` зовут
   `POST shop /turn {episode_id, channel, text, turn}` (`services/shop/app.py:301`).
3. `shop /turn` возвращает **только** `{text, ended, session_status}`; сырьё
   (решения гвардрейлов, вызовы инструментов, llm_calls, снимок состояния)
   доставляется в `filter /record` изнутри (`_deliver`, `services/shop/app.py:366`).
4. `filter /record` пишет сырьё в свою БД под строкой хеш-цепочки (`lab/chain.py:32`);
   `raw.llm_calls` дополнительно оседает кассетными строками (`lab/cassette.py`).
5. `metrics /compute` читает сырую БД read-only и считает L*/break-even/detection
   (`services/metrics/formulas.py:97`); результат в свою БД; вызывать можно в любое
   время, правка формул не требует перезапуска прогонов.

   Сервисы и launcher должны использовать согласованное окружение: один
   `LAB_RUNS_DIR` для манифестов и один `LAB_RAW_DB_URL` для filter/metrics.
   Иначе запускаются две параллельные БД, а расчёт не видит эпизодов кампании.

## Критичные инварианты (не ломать)

1. **Барьер «только текст»**: наружу от СС не выходит ничего, кроме текста ответа.
   Сырьё уходит в filter_svc только изнутри shop_svc. Тест: `tests/test_shop_service.py`
   (turn возвращает ровно три поля) и `tests/test_filter_service.py` (в /text нет полей raw).
   Если добавляешь поле в ответ /turn — это дыра в барьере, так нельзя.
2. **Атакующий без доступа к коду защиты и БД** (`services/attack/`): только HTTP
   `POST /turn` с `channel="attack"` и goal ячейки; никакого прямого чтения БД
   магазина, никаких решений гвардрейлов в контексте атакующего; брифа от shop
   нет — system-промпт собирается attack-сервисом из frozen (манифест мира +
   реестры целей/методов + тон).
3. **traffic_svc читает БД магазина read-only** — это разрешено схемой (чтение для
   правдивых запросов). Писать из traffic в БД магазина нельзя.
4. **Пин model_spec**: каждая запись несёт, на какой модели гоняли —
   `episode_start` в журнале shop, `model_spec` в каждом /record, `manifest.json`
   launcher'а, `metric_results` metrics. Ростер — `frozen/llm.json`; модели из него
   не удалять молча (смена — осознанный коммит).
5. **Хеш-цепочка append-only** (`lab/chain.py`): перезапись payload ломает verify.
   Обрезка хвоста по построению не обнаружима — это crash-safe свойство, не баг
   (тест это документирует). Пиши только в конец.
6. **Кассеты**: одна строка на пару запрос→ответ к модели. Если добавляешь вызов
   модели в любом сервисе — он должен попасть в `raw.llm_calls` записи filter.
7. **Сбор ≠ расчёт**: в сервисах прогона (shop/traffic/attack/filter) никаких
   метрик. Всё вычисление — только в `services/metrics/`, поверх сохранённого.
8. **Парные прогоны**: legal- и attack-эпизоды ячейки стартуют с одного исходного
   состояния — reset → configure → snapshot → эпизод → restore между членами пары
   (`launcher/campaign.py`) — и ведутся **в одном стиле общения** (`frozen/styles.json`:
   стиль передаётся в обе ноги пары, атакующему — тон-клаузой в system-промпт,
   стартовая реплика остаётся корпусной). Не убирай restore и не разъединяй стиль:
   иначе тон становится конфаундом детекции.
8d. **Путаница — свойство только легальной ноги** (dvarp-lab#56): ось `confusion`
    (`frozen/corpus/confusion.json`) добавляет честному правдивому клиенту
    редкий шум — неуверенность в датах/количествах, опечатку в названии товара,
    случайно вставленный «технический» текст (скопированная ошибка сайта,
    фрагмент из письма поддержки). Почему это не завышение FP: события правдивы
    (меняют формулировки, не факты), редки (одно на эпизод, выбор от сида) и
    реалистичны по частоте — FP на честно-запутанном трафике есть настоящий FP;
    «святоша»-нога без путаницы — это искусственно заниженный FP. Якорь `none`
    сохраняет нижнюю границу вреда (формулировка «lower bound» остаётся); режимы
    дают оценку на реалистичном честном трафике и гоняются отдельными прогонами
    (по-режимные R/FP/G-τ через run_id-разрез #49, формулы не правятся). Сид
    производных и id обеих ног включают режим → независимые ресэмплы атак по
    режимам и уникальные legal-эпизоды. Не накачивай частоту триггерных слов —
    это превращает честный шум в скрытую атаку.
8a. **UI/probe**: консоль (`services/ui`, 9410) — только читатель/вызыватель,
    ноль расчётов; запуск — те же `run_campaign/probe`, что у CLI. Фронт только
    рисует: форма, пресеты и словарь терминов — данные `services/ui/describe.py`
    через `/api/meta`; одноразовый расчёт — `metrics /preview` (не пишет). Probe-атаки
    (`raw.probe=true`) по умолчанию исключены из метрик — не убирай фильтр.
    Выбор эпизодов и метрик — через справочные read-only эндпоинты
    (`filter /episodes`, `metrics /configs`); оглавление-чекпоинты метрик —
    клик к карточке конфига; русские сноски терминов — тултипы при наведении.
8c. **Remote LLM**: любой http(s) эндпоинт разрешён по умолчанию, без флагов
    (облачные прокси AITunnel и т.п. — для разработки и тестов); локальный
    контур = loopback (127.0.0.1/::1/localhost). Не-локальный эндпоинт
    **маркируется автоматически**, guard тройной: пин `"remote_llm": true` в
    манифесте (launcher по env-эндпоинтам, `lab.nominal.remote_endpoints`);
    `raw.remote_llm=true` в записях (каждый сервис по своему эндпоинту);
    метрики пропускают эпизод целиком, если remote хоть одна его запись
    (`include_remote` — явная опция). Данные статьи — только локальные
    эндпоинты (NFR-2.4/2.5, канон не меняется). Флаги `allow_remote_llm` /
    `LAB_ALLOW_REMOTE_LLM` устарели: принимаются и игнорируются. Ростер — не
    гейт: имена вне `frozen/llm.json` пинуются `remote-verification`
    (`params_b=None`); размер (NFR-2.6) — fail-closed, как раньше.
    Клиент: OpenAI-совместимый (base_url + модель + Bearer-ключ в env:
    `LAB_CUSTOMER_LLM_*`, `LAB_ATTACKER_LLM_*`, у агента — канонические
    `RESEARCH_LLM_*`). На remote-прогонах L* считается
    полноценно (галочка include_remote) — формулы и различия конфигов проверяются
     на живом материале; в датасет статьи эти числа не идут.
     Результаты `metric_results` разнесены по `mode=local/remote/all`;
     `all` — явно запрошенный совместный расчёт, не данные статьи. Число
     remote-эпизодов видно в `n_remote`. Сид live-прогона — метка группы
     вариативности сэмплинга LLM, а не гарантия повторяемости ответа.
8b. **Семантика сида (ревизия «один мир», dvarp-lab#6)**: БД магазина — один
    замороженный мир (`frozen/seed_worlds/world_a/`), тот же мир → байт-идентичная
    БД; сид данных не касается — он детерминирует только прогон (раскладка
    реплик stub-клиента/атакующего и пр.). Легальный эпизод опирается на один
    фиксированный всегда-возвратный заказ A из манифеста мира (кейс не
    перебирается сидом; у легального варьируется только ось стиля). Кейс
    атакующего определяется целью (`frozen/corpus/goals.json`: цель → заказ мира
    или фиктивный заказ из манифеста), а не pool[0]. Оси перебора — цели ×
    методы × тон; прежние оси миров/когорт выпали. Снапшот пары — от мира
    (снимок после reset, до эпизодов); meta БД пиннит `world`/`dataset_hash`.
8b-r. **Роли вне БД**: привязка ролей (legal/attack) — манифест мира (файл
    frozen), который shop_svc читает при open эпизода; в БД не остаётся ни
    одного следа роли/атакующего (тест-инвариант чистоты БД,
    `tests/test_shop_service.py`, `tests/test_world.py`). Атакующий не знает
    своей «роли» из БД — её просто нет.
8d. **NFR-2.8 (прогон-микс) — интерпретация** (владелец, 2026-11-25): кампания
    лаба соответствует ревизии канона 2026-11-13 «смешанный поток эпизодов» —
    каждая ячейка содержит legal+attack ноги на идентичном начальном состоянии
    (snapshot/restore), кампания в целом = смешанный поток. «Парные прогоны» в
    словаре лаба — это общий стиль пары (инвариант 8), а не исключённые каноном
    «парные легальные потоки». canon-request не требуется.
9. **Номинальная проверка перед каждым прогоном** (`lab/nominal.py:check_config`):
   конфиг из frozen/configs. Локальность эндпоинтов и ростер не гейтят, а
   маркируют (8c). Сети не блокируются, проверка номинальная, при старте.
10. **frozen/ меняется редко и осознанно**: конфиги защиты, ростер моделей, корпус
    атак, стили общения — замороженные характеристики исследования.

## Запреты для агентов (чтобы не раздуть)

- Dockerfile/CI/мутационные скрипты/гейты — нельзя: только код + pytest +
  openspec. Дисциплина: `uv run pytest`; pre-commit — ruff (nixpkgs) и
  `openspec validate --all`; содержательное изменение коммитится вместе с
  дельтой `openspec/changes/<change-id>/`.
- Коммиты: Conventional Commits на английском, `git -c commit.gpgsign=false`;
  пуш — только после приёмки владельцем.
- Не переносить из прототипа лишнее: replay, isolation, svckit, report_cli,
  freeze-машинерию — здесь это выброшено сознательно.
- Секреты/`.env*` не читать; ключи LLM — только в env процесса, в журнал/манифест
  не попадают.
- Канон исследования — репо `CloudNative-urfu/dvarp` (FR-1.x/NFR-2.x): из задач
  dvarp-lab напрямую не редактируется; расхождения — заявка в `canon-requests/`
  в том же коммите + сообщение владельцу (см. `canon-requests/README.md`).

## Решение: где гоняются эксперименты статьи (зафиксировано 2026-11-22)

**Эксперименты научной статьи (кампания прегрегистрации и n³-прогоны) проводятся
на dvarp-lab.** Кластер репозиториев полигона (polygon-*, ag-*) — продуктовый
трек, для статьи он не используется; после публикации возможна репликация
чисел на кластере как приложение.

Обоснование:

1. **Воспроизводимость**: пиннинг для ревьюеров — один коммит dvarp-lab +
   `uv.lock` + `frozen/` + манифесты/кассеты/цепочки; у кластера — 10 репозиториев,
   10 пинов, deploy-топология и контейнеры, т.е. на порядок больше источников
   недетерминизма, не влияющих на измеряемую защиту, но осложняющих повторение.
2. **Измеряемый объект тот же**: защита в dvarp-lab и в ss-refund-shop перенесена
   из одного среза исходника (d5828df) — эксперимент измеряет ровно ту защиту,
   что живёт в продукте; топология деплоя не является предметом статьи.
3. **Цена верификации**: проверить корректность прогонов в dvarp-lab — чтение
   пяти небольших сервисов за вечер; в кластере — ревизия 10 репо + deploy + сетевых
   стыков, кратно дольше, и каждое звено — потенциальный дефект, портящий числа.
4. **Независимость от чужого темпа**: кампания статьи не зависит от готовности
   ag-harness/polygon-deploy (они двигаются под продукт).

Ревьюер оценивает доказательность прогона (пины, seeds, сырые данные, процедура),
а не размер системы; сервисность dvarp-lab — для читаемости кода, не для прод-топологии.

## Roadmap исследования

1. **Стенд** — готов (сквозной смок зелёный, консоль 9410);
2. **Live-подключение моделей** — ждёт локальный эндпоинт (issue #84
   dvarp-prototype); до него — stub-прогоны;
3. **Пилот** — 1–2 конфига live: throughput (сколько воркеров нужно) + пригодность
   базового атакующего (рождаются ли нарушения; усиление — адаптивная память из
   прототипа, если нет);
4. **Прегрегистрация** — пин: коммит репо + `uv.lock` + sha256 `frozen/*` + ростер
   моделей + план кампании;
5. **Кампания** (n³: конфиги × модели × сценарии × миры-сиды);
6. **Статья** (USBEREIT/IEEE), затем репликация на кластере полигона.
