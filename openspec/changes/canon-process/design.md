# Design: canon-process

## Решения

- **Механика заявок — копия прототипа, счётчик — свой**: формат/шаблон/
  каталоги (`pending/` → `accepted/`) взяты из
  `dvarp-prototype/canon-requests/` как проверенные; нумерация NNN
  начинается с 001 независимо от прототипских заявок (другой репозиторий,
  другой реестр).
- **Заявка в том же коммите, что и изменение**: в лабе нет PR-процесса
  (пуш в main после приёмки), поэтому связка «заявка + вызвавшее её
  изменение в одном PR» переосмыслена как «в одном коммите» + упоминание
  в openspec-change того же issue.
- **Владелец уведомляется при создании заявки** (issue/чат), а не в
  момент PR в `dvarp`: решение о правке канона — за владельцем; заявка
  фиксирует расхождение до решения.
- **Не вербализуем замену «спросить владельца» на «заявку»**: вопрос
  владельцу остаётся первым шагом (уведомление), заявка — трассируемая
  форма фиксации расхождения.
- **Защита main — API без bypass прямых пушей**: правило «всё через PR»
  действует и на владельца (branch protection c enforce_admins);
  аппрув-требование для PR тимлида обходится
  `bypass_pull_request_allowances` (axstiz) — саморевью по устному
  правилу, но merge по-прежнему только через PR.

## Риски

- Реестр заявок в README — ручная таблица: при активной фазе кампании
  может отставать; дисциплина — обновлять в том же коммите переноса.
