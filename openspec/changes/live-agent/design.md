# Design: live-agent

## Решения

- **Sink, а не переиспользование Recorder**: у shop-агента свой путь записи
  (журнал пишет только хеши — приватность по дизайну), поэтому тексты пар
  запрос→ответ собираются опциональным `sink`-списком на уровне
  `ChatModel.complete` и доставляются в filter через `raw.llm_calls`
  (тот же ключ, что у traffic/attack Recorder). Барьер не тронут: наружу
  `/turn` возвращает только текст.
- **Доставка с очисткой**: `ep.llm_calls.clear()` после успешной
  `/record` — кассетные строки не дублируются по ходам; при недоставке
  эпизод помечается error, буфер сохраняется и уйдёт следующим ходом.
- **Bypass ростера в /configure — по env, не по телу запроса**: тот же
  источник, что у агента (`LAB_ALLOW_REMOTE_LLM=1` в env shop-процесса) —
  сервис не доверяет пину из сети; launcher передаёт имя модели, а решение
  о допуске принимает конфигурация процесса.
- **`params_b: float | None`**: честный пин remote-модели без известного
  размера; fail-closed перенесён в сборку live-клиента (явная ошибка про
  `RESEARCH_LLM_PARAMS_B` вместо TypeError).
- **UI prefill из env ui_svc**: ui живёт в том же dev-процессе, что
  сервисы (dev.py передаёт детям копию окружения), поэтому имена моделей
  читаются из своего env; ключи и base_url не раскрываются никогда.

## Риски

- Remote-кампания может пронести off-roster пины в данные — ограничено
  существующим тройным guard (манифест, `raw.remote_llm`, пропуск
  метрик по умолчанию); данных статьи не касается.
